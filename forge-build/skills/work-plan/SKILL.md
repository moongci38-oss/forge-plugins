# work-plan — 작업계획서 한 양식

> 설명 원문(#3691 목록 예산으로 줄이며 여기로 옮김): 작업계획서를 이슈 단위 한 양식으로 쓰고 검사기로 확인해 저장한다. 사용자가 '계획 세워'·'작업계획서'·'plan 짜줘'·'계획서 써줘'를 요청할 때 쓴다. SKIP: 한 건이면 바로(버그 /forge-fix · 그 밖 /forge-implement) · Spec 문서는 /forge-spec.

**역할**: 요청을 **이슈 단위**로 나눠, 이슈마다 담당·검수·진행 순서·테스트 계획·완료 기준을 적은 계획서를 쓴다. 사람이 읽고 바로 알아듣는 쉬운 말로.
**컨텍스트**: 사람이 "계획 세워"·"작업계획서"를 요청할 때. 계획만 쓴다 — 코드·설정은 고치지 않고, 이슈 등록도 **승인 뒤**에 한다.
**쓰는 때**: 여러 건을 나눠 맡기거나 승인·묶음(마일스톤)이 필요할 때만 — 한 건은 바로 `/forge-fix`·`/forge-implement`. 경계 정본 `${FORGE_ROOT:-$HOME/forge}/.claude/rules-on-demand/harness-family-map.md`.
**출력**: 계획 폴더의 `YYYY-MM-DD-<slug>-plan.md` 1개(파일이 정본) + 검사기 `OK` 줄 + 필요하면 같은 내용의 아티팩트.

## 절차

1. **실측** — 요청에 걸린 코드·문서·이슈를 읽는다. `## 왜 하나` 에 `실측: \`<명령>\` → <본 결과>` 를 1줄 이상 남긴다. 모르면 "확인 필요"(추측으로 채우지 않는다).
   - **intent** — `${FORGE_ROOT:-$HOME/forge}/docs/intent/STEP.md` 를 Read 해 따른다(이 변경의 intent 가 없으면 먼저 만든다 · `상태: draft` 로도 진행 · 계획서 `## 왜 하나` 의 근거).
2. **쓰기** — 틀은 `assets/plan-template.md`(쓸 때 Read). 절 순서·이름을 바꾸지 않는다. 규칙 문장을 베끼지 말고 틀의 괄호 속 지침 경로를 가리킨다.
   - 이슈마다 `### 이슈 N` 블록: 등록 · 담당·검수 · 진행 순서(테스트 먼저면 실패 테스트부터) · 테스트 계획 · 완료 기준(`\`<명령>\` → <기대>` — 이 줄이 이슈의 `## 확인 방법` 이 된다).
   - 담당·검수는 손으로 고르지 않는다 — `issue-owner.sh owners <레포> <라벨>` / `reviewers` 출력값을 적고 그 명령을 괄호로 단다.
   - **짧은 꼴**: 이슈가 1개면 한 줄 요약 · 왜 하나 · 안 할 것 · `### 이슈 1` 블록만 써도 된다. 이슈 2개 이상이면 한눈 표·끝나면 달라지는 것·진행 방식·위험과 되돌리기·사람이 정할 것까지 다 쓴다.
   - **적용 범위**는 기본이 전 프로젝트·전 팀원이다 — `적용 범위: 전 프로젝트·전 팀원` 또는 `적용 범위: 제외 — <무엇> · <이유>` 1줄(짧은 꼴도 필수). 전 팀원이면 완료 기준에 배포 길(전역 등록 → team-stable 승격 → 팀 PC 반영 확인) 1줄을 둔다(`team-stable-promote.sh` · `pc-status.sh`).
   - **묶음**: 계획서 1장 = 새 묶음(마일스톤) 1개 — `## 이슈별 계획` 한눈 표 위에 `- 묶음: patch-YYYY-MM-DD · 새로 만듦 · 목표일 <날짜> · 허브 묶음이 끝나면 기계가 만듦` 1줄(이슈 2개 이상 필수 · 같은 계획의 후속처럼 기존 묶음이면 `기존 — <사유>` · 이슈 1개면 `해당 없음 — <사유>` 도 된다). 이슈 블록 `등록:` 의 `묶음 <이름>` 은 이 이름과 같아야 한다.
   - 해당 없는 칸은 `해당 없음 — <사유>` 1줄. 빈 칸·빈 절은 안 된다.
3. **검사** — 저장 폴더는 손으로 정하지 않는다:
   ```bash
   DIR=$(python3 "${FORGE_ROOT:-$HOME/forge}/shared/scripts/work-plan-lint.py" --plan-dir)
   python3 "${FORGE_ROOT:-$HOME/forge}/shared/scripts/work-plan-lint.py" "$DIR/<파일>.md"
   ```
   폴더 순서: 환경변수 `WORK_PLAN_DIR` → `<프로젝트 루트>/.claude/work-plan.json` 의 `plan_dir` → 기본 `${FORGE_OUTPUTS:-$HOME/forge-outputs}/docs/planning/active/plans`(없으면 `mkdir -p`). rc 1 이면 지적 줄을 모두 고치고 rc 0 까지 다시 돌린다.
   - 검사기 OK 뒤 `python3 "${FORGE_ROOT:-$HOME/forge}/shared/scripts/work-plan-html.py" "$DIR/<파일>.md"` 로 같은 이름 `.html` 을 만든다(이슈 링크 레포는 지금 폴더 git origin · 다르면 `--repo <owner/name>`). 사람에게는 HTML 경로를 보인다(공유가 필요하면 아티팩트로 발행) — 정본은 마크다운이다.
4. **사람 승인** — 파일 경로 · 검사기 `OK` 줄 · 사람이 정할 것을 쉬운 말로 보고하고 멈춘다. 승인 전에는 이슈를 만들지 않는다.
   - **검수 자동 호출(#3608 · 사람 결정 2026-10-24 · Codex 단독 2026-10-27 #3897)** — 검사기 OK·HTML 뒤, 사람 승인 보고 **전에** `bash "${FORGE_ROOT:-$HOME/forge}/shared/scripts/review-4lens.sh" --stage plan --target <계획서 md 경로> --root <계획서가 든 레포 절대경로>` 를 **부른다**(묻지 않는다 · 통합 입구 `codex-review-route.sh --stage plan --mode 4lens` 가 고르는 엔진 = Codex 4관점 동시 · 읽기 전용 · 계획서 레포가 CWD 밖이면 `--root` 가 있어야 한다).
     - 부르기 **전에** 시크릿 사전 스캔: `bash "${FORGE_ROOT:-$HOME/forge}/shared/scripts/forge-multi-prepare.sh" <계획서 md 경로> --stage plan` — rc 1(`SECRET=blocked`)이면 부르지 않고 사람에게 "계획서에 비밀값 의심 — 외부 전송 중단"을 보고한다(사람 opt-in 없이 Codex 로 가는 길이라 빼먹지 않는다 · review-4lens.sh 안 거르개보다 먼저 막는다).
     - 예산: 계획서 1장당 **1라운드**(운영 규칙 1). LOW·비차단 지적은 버린다(운영 규칙 3). blocking 지적은 계획서를 고치고 검사기를 다시 돌린 뒤 승인 보고 — 두 번째 검수는 부르지 않는다(사전 스캔이 원장으로 판정 — 고친 계획서는 rc 3 `ROUND=exhausted` 면 부르지 않는다 · #3666).
     - 종료 코드: 0 = PASS · 1 = FAIL(blocking = `BLOCKING=` 수 · 지적은 `OUT_DIR` 의 `lens-<n>.md`) · 3 = Codex 못 돎(한도·장애) → Claude 검수자 대체: code-reviewer 4명을 한 메시지에서 동시에(프롬프트 = 계획서 경로 + 관점 이름 하나 · 관점 정본 `shared/config/review-lenses.md`) · 승인 보고에 `검수: <판정> · 벤더 claude` 1줄(`model-routing.md` 검수 줄 · #4219) · 4·2 = 검수 못 함(형식 실패·대체 끄개 off 등 — 막지 않는다 · 승인 보고에 `검수: 못 함 — <REASON>` 1줄).
     - 부르지 않는 때: 이슈 1개짜리 짧은 꼴 계획서(1건은 원래 work-plan 대상이 아니다) · 사람이 "검수 빼고" 라고 한 때 · 읽기 세션(`--readonly` — 검수 증거·원장을 쓰는 일이라 읽기 세션 몫이 아니다 · #3666) — 승인 보고에 `검수: 안 함 — <사유>` 1줄.
     - 승인 보고에 결과 1줄: `검수: <판정> · blocking <n> · 고침 <n>`.
5. **승인 뒤 이슈 등록**(이슈 먼저 — 담당 방에 넘기기 전 · `harness-family-map.md` §이슈 먼저) — 등록 **전에** 승인을 확인한다 — 순서: ①계획서를 커밋·push 해 develop 에 올린다 ②승인 코멘트를 달 이슈를 정한다(이 계획을 요청한 이슈 · 없으면 `issue-new.sh` 로 `계획 승인: <계획서 제목>` 1장) ③사람이 그 이슈에 계획서 경로를 적은 승인·결정 문장을 쓴다(`docs/intent/STEP.md` 4번) ④그 문장이 없거나 총괄이 이슈에 반영하지 않았으면 등록하지 않고 멈춘다(사람 키 서명은 없앴다 — #4080). 그 뒤 한눈 표의 `등록 예정` 줄마다 `issue-new.sh`(라벨·`--owner`·`--reviewer` 는 그 머리말)로 등록한다. 이슈 본문에 그 블록의 진행 순서·테스트 계획을 옮기고 완료 기준 줄을 `## 확인 방법` 으로 넣는다.
   - 등록하면 **정본은 이슈 본문**이다 — 계획서의 그 블록은 `- 이슈: #N (정본 — 상세는 이슈 본문)` + 담당·검수 1줄로 줄이고, 표의 `등록 예정` 을 `#N` 으로 되적는다. 계획서에는 한눈 표·이슈 링크·진행 방식만 남는다. 묶음이 있으면 마일스톤을 붙인다(아래).
   - **묶음 만들기**(새로 만듦일 때만 · 총괄 PC): `bash ${FORGE_ROOT:-$HOME/forge}/shared/scripts/bundle-report.sh --init <이름> --title "<계획서 한 줄 요약>"` → 마일스톤 설명 둘째 줄을 `gh api -X PATCH repos/<레포>/milestones/<번호> -f description="<한 줄 요약>"$'\n'"계획서: <HTML 경로> (정본 <md 경로>)"` 로 채운다(허브 제목은 첫 줄, 개요는 전부 싣는다). 이름이 이미 있어 거부되면 목표일을 하루 옮겨 계획서의 묶음 줄·블록 묶음 칸을 같이 고친다.
   - 등록한 이슈마다 마일스톤을 붙인다: `gh api -X PATCH repos/<레포>/issues/<N> -F milestone=<번호>`.
   - 고친 계획서를 검사기로 다시 돌려 rc 0 을 확인하고, `work-plan-html.py` 로 HTML 도 다시 만든다.
6. **담당 방에 내려보내기** — 담당 방에 일을 넘길 때는 브리프 11요소(`advisor-worker-delegation.md` §브리프 11요소 템플릿)로 쓴다.

## 하지 않는 것
- 프로젝트·조직·PC 이름이나 절대 경로를 이 스킬·양식에 박지 않는다 — 저장 위치는 설정 데이터(`.claude/work-plan.json`)로만 바꾼다.
- 계획을 세운 김에 구현을 시작하지 않는다.

## 실패 시 출력
- 검사기 rc 1 → 지적 줄(`<파일>:<줄>: <지적>`)을 그대로 보이고 고친 뒤 재실행. 3번 넘게 같은 지적이면 그 줄과 함께 "미완료"로 보고한다.
- 검사기 rc 2 → 사용법·파일 경로 오류 1줄을 보이고 멈춘다.
- 근거를 실측할 수 없으면 해당 칸에 "확인 필요"를 적고 `## 사람이 정할 것` 에 올린다.
- 검사기는 담당·검수 값이 진짜 방 이름인지는 보지 않는다 — `issue-owner.sh` 출력과 맞는지는 쓰는 쪽이 지킨다.
