# Development Workflow Rules (요약)

> 원문(근거: · 폐기조건: · 이력) → `rules-on-demand/dev-workflow-rules-full.md` · 절차 상세 → `rules-on-demand/dev-workflow-detail.md`

## 운영 규칙 (이 절이 다른 규칙보다 우선)
1. **완료 = 테스트 통과 + blocking 0.** 검수는 훅·권한·보안·머지 규칙을 바꿀 때만, **PR 당 1번 · 검수자 4명이 관점 하나씩 동시에**(Codex 4갈래 `review-4lens.sh` #3897 · 1회 · 1벤더 · 브리프 1개 — ①우회·주입 ②회귀 ③변형·전수 ④실사용·배선). **검수는 그 프로젝트의 `qa-<프로젝트>` 방이 한다** — 총괄은 `review-brief.sh` 브리프 경로만 보낸다 · qa 방이 지적을 합쳐 CRITICAL·HIGH 만 판정 코멘트에 적고 qa wisdom 1줄을 남긴다 · `reviewer:` 라벨 = **모든 카드**의 검수 방(4관점은 위 범위만 · 그 방은 `## 사람 확인` 줄만 재확인). CRITICAL·HIGH 만 고치고 **끝낸다** — **재검수 없음**: **기계 검사 줄(`fail=0 miss=-`)과 그 지적의 테스트 칸**으로 확인해 머지한다. 이슈는 `## 확인 방법` 실측이 통과해야 닫힌 채로 남는다(`issue-verify.sh`) · 새 스크립트 미배선은 머지 거부.
   - **동작 불변 리팩토링은 검수 없이 기계 검사로 머지한다**(모든 프로젝트 레포 같음 · #3342) — 조건(제목·전후 동일 증명·`판정 바뀐 줄: 0`) = `cr-risk-tier.sh` refactor-tier-exempt.
2. **실행 방식을 먼저 고른다** — 병렬 서브에이전트·워크플로·에이전트 팀·혼자 순서대로(`forge-core-full.md`). 독립 일은 반드시 병렬(같은 파일만 순서) · 방당 동시 최대 10(읽기 전용 탐색 제외). 서브에이전트 변경은 팀장이 확인(PR 본문 `실행 방식:`·`## 팀장 확인`).
   - full-gate 검수 관점 4개는 개수에 넣지 않는다 — 검수자는 읽기 전용이고 PR 당 1회뿐이다.
   - 구현·수정·병렬·워크플로는 담당 팀장 방이 한다 — 총괄은 배정·검수 의뢰·머지만(`orch-impl-spawn-check.sh`).
   - 읽기 전용 세션도 총괄 방식 — 쓰기 방엔 읽기 질의만(`send --ask`) · 읽기 방(mode=read)엔 브리프 · 고칠 코드는 `issue-new.sh` 로 등록.
3. **LOW·비차단 지적은 버린다.** 지금 실제로 일어나지 않는 경우(가정·위조·아직 없는 설정)를 전제로 한 지적은 등급과 무관하게 버린다. **후속 지적은 CRITICAL·HIGH 만 이슈** · 그 밖은 주간 묶음 허브에 1줄. 등록 전에 열린 같은 주제 이슈를 찾고, 있으면 그 이슈의 할 일 줄로 더한다. 하네스 갭 A·B·C → `dev-workflow-rules-full.md`.
4. **하네스 변경 = A칸 + 승인된 B칸 + 사람 요청.** 동시 진행 **최대 10** — ①같은 파일(스테이지는 대상 경로)은 동시에 두지 않는다(점유 = 배정~머지 · 뒤에 온 일이 기다린다) ②진행 중(`status:doing`)이 3일 움직임 없으면 `status:blocked` 로 내리거나 내려놓는다.
5. **방(room)은 제품 작업과 하네스 일에 쓴다** — 하네스 작업 방은 2개 · 같은 파일은 한 방 · 방 규약 → `rules-on-demand/team-routing.md` · 팀 목록 정본 = 이름표 `members/<slug>/identity.md`.
6. **검수에서 프로그램으로 되는 일(테스트·변이·구문·린트·타입·빌드)은 프로그램이 1번 돈다** (`machine-checks-line.sh`) — 검수 레그는 판단만. 스테이지 PR 은 총괄이 먼저 적용한 뒤 기계 검사.
7. **PR 은 작게 · 시험은 꼭 필요한 것만 · 머지는 묶어서**(#3199) — ①PR = 한 이슈 · 바꾼 줄 중심 ②시험은 그 버그·기능을 막는 것만(버그 1건 = 시험 1개) (③ 묶음·가벼운 관문 → `dev-workflow-rules-full.md`) 예외 = 계측기·관문 변경은 하나씩 머지.

## 설계 원칙
- **OOP**(SOLID·캡슐화·합성) · **DDD**(용어·경계·불변식·의존은 안쪽으로) · **SDD**(스펙 먼저·FR 추적) · **TDD**(테스트 먼저·red-green·변이) — 설계·구현·리뷰 **전 단계**에 적용. 정본 → `rules-on-demand/design-principles.md`.

## Git
- develop 에 먼저 커밋/푸시 · 배포 브랜치(main·production) 직접 커밋 금지. 신규 브랜치는 develop 분기(hotfix/* 예외).
- develop 머지는 AI 가 한다(squash · 머지 전 판정 코멘트 1줄) — **단 총괄 세션만**. 방은 **판정 코멘트까지** — 방 세션의 머지는 `pr-merge.sh` 가 거부한다. 브랜치는 머지 또는 아카이브로 끝낸다.
- **빌드·배포(dev·stg)·클라 빌드·슬랙 게시는 그 프로젝트의 배포 스크립트로만**(또는 준비된 배포·운영 MCP) — 손 단계 금지 · 입구 = `deploy-entry.sh <레포> <칸>` · rc 3(스크립트 없음)이면 손 작업 대신 보고 + 그 프로젝트에 스크립트 만드는 이슈(`/forge-deploy` §입구 표).
- 머지마다 구문 검증(`bash -n`·`py_compile`·`node --check`·JSON).
- 워크트리는 머지되면 기계가 지운다(`worktree-gc.sh`) — 남아 있으면 `engine-report.sh`.
- 공유 체크아웃이 막히면 임시 워크트리 cherry-pick(D-2) · ⛔ `git stash`/`--autostash` 금지 · ⛔ 남의 파일 커밋 금지.

## 세션 경계
- 플랫폼 세션(forge·forge-outputs)은 제품 코드를 고치지 않는다 — 제품 repo 일은 위임 브리프로.
- 세션은 연 프로젝트 **그리고** 이 PC(`pc:`) 몫만 작업한다(코드·장부·이슈·문서 모두). 범위 밖은 개수만 적는다. '다 해' 는 이 범위 안의 전부다. 예외: forge 레포의 읽기 세션(`--readonly`)은 전 프로젝트를 읽고 조언한다 — 쓰기·진행은 없다.
- 작업 세션을 끝낼 때는 **요청이 없어도 `/forge-end`**(팀장 방은 버스 교체 체크포인트).
- 깰 때마다 **점검 사이클 1회** → `rules-on-demand/session-cycle.md`.
- 끊겼다 이어갈 때 첫 행동은 실측 — `git log -3`·`gh pr view` 로 마지막 비가역 행동을 확인한 뒤 계속한다.
