# Development Workflow Rules (요약)

> 원문(근거: · 폐기조건: · 이력) → `rules-on-demand/dev-workflow-rules-full.md` · 절차 상세 → `rules-on-demand/dev-workflow-detail.md`

## 운영 규칙 (이 절이 다른 규칙보다 우선)
1. **완료 = 테스트 통과 + blocking 0.** 검수는 훅·권한·보안·머지 규칙을 바꿀 때만, **PR 당 1번 · 검수자 4명이 관점 하나씩 동시에**(1회 · 1벤더 · 브리프 1개 — ①우회·주입 ②회귀 ③변형·전수 ④실사용·배선). **검수는 그 프로젝트의 `qa-<프로젝트>` 방이 한다** — 총괄은 `review-brief.sh` 브리프 경로만 보낸다 · qa 방이 지적을 합쳐(같은 파일·같은 줄 = 1건) CRITICAL·HIGH 만 판정 코멘트에 적고 qa wisdom 1줄을 남긴다. CRITICAL·HIGH 만 고치고 **끝낸다** — **재검수 없음**: 수정본은 다시 검수하지 않고 **기계 검사 줄(`fail=0 miss=-`)과 그 지적의 테스트 칸**으로 확인해 머지한다(두 번째 브리프는 `review-brief.sh` 가 만들지 않는다). 이슈는 `## 확인 방법` 실측이 통과해야 닫힌 채로 남는다(머지 뒤 `issue-verify.sh` — FAIL·NONE 이면 다시 연다) · 새 스크립트 미배선은 머지 거부.
2. **실행 방식을 먼저 고른다** — 병렬 서브에이전트·워크플로·에이전트 팀·혼자 순서대로(`forge-core-full.md` 4분법 · 갈리면 CTO·PMO). 기본 = 이슈 단위 병렬 · 큰 이슈 쪼개기는 파일별로 깔끔히 갈릴 때만(팀장 검증). 방당 동시 최대는 고정하지 않는다(처음 3 · 올릴 땐 측정값으로 사람에게 묻는다 · 같은 파일은 하나씩). 서브에이전트 변경은 팀장이 직접 확인한다(PR 본문 `실행 방식:`·`## 팀장 확인`).
   - full-gate 검수 관점 4개는 개수에 넣지 않는다 — 검수자는 읽기 전용이고 PR 당 1회뿐이다.
   - 읽기 전용 탐색 에이전트(쓰기 도구 없는 Explore·Plan + 브리프에 쓰기 금지)도 넣지 않는다 — 쓰기 도구가 있으면 안 써도 센다.
3. **LOW·비차단 지적은 버린다.** 지금 실제로 일어나지 않는 경우(가정·위조·아직 없는 설정)를 전제로 한 지적은 등급과 무관하게 버린다 — 필요하면 이슈 1줄. 하네스 갭은 입구 1개(라벨 `harness-gap` · `재현:` · `막힌 것:`) — A 막힘 = AI 가 바로 처리 · B 불편 = 주간 묶음 사람 승인 · C 나머지 = 이슈 만들지 않음.
4. **하네스 변경 = A칸 + 승인된 B칸 + 사람 요청.** 동시 진행 **최대 6** — ①같은 파일(같은 레포의 같은 상대경로 · 스테이지는 실제 대상 경로)을 건드리는 일은 동시에 두지 않는다 · 점유는 배정부터 머지·닫기까지 · 겹치면 뒤에 온 일이 기다린다 ②머지는 §Git.
5. **방(room)은 제품 작업에만.**
6. **검수에서 프로그램으로 되는 일(테스트·변이·구문·린트·타입·빌드)은 프로그램이 1번 돈다** — 줄은 `machine-checks-line.sh` 가 만들고 머지 관문이 표식을 본다 · 검수 레그는 판단만. 스테이지가 있는 PR 은 **총괄이 스테이지를 가지에 먼저 적용한 뒤** 방이 기계 검사를 돌린다 — 그 뒤 문서·증거만 바뀐 커밋에는 직전 통과 줄을 인정한다.

## 설계 원칙
- **OOP**(SOLID·캡슐화·합성) · **DDD**(용어·경계·불변식·의존은 안쪽으로) · **SDD**(스펙 먼저·FR 추적) · **TDD**(테스트 먼저·red-green·변이) — 설계·구현·리뷰 **전 단계**에 적용. 정본 → `rules-on-demand/design-principles.md`.

## Git
- develop 에 먼저 커밋/푸시 · 배포 브랜치(main·production) 직접 커밋 금지. 신규 브랜치는 develop 분기(hotfix/* 예외).
- develop 머지는 AI 가 한다(squash · 머지 전 판정 코멘트 1줄) — **단 총괄 세션만**. 방은 **판정 코멘트까지** — 방 세션의 머지는 `pr-merge.sh` 가 거부한다. 브랜치는 머지 또는 아카이브로 끝낸다.
- 머지마다 구문 검증(`bash -n`·`py_compile`·`node --check`·JSON). "충돌 없음" ≠ 안전.
- 워크트리는 머지되면 기계가 지운다(`worktree-gc.sh`). 머지됐는데 남아 있으면 하네스 결함 → `engine-report.sh`.
- 공유 체크아웃이 막히면(병행 세션 dirty tree 가 push 를 막는 등) rebase 대신 임시 워크트리 cherry-pick(D-2) · ⛔ `git stash`/`--autostash` 금지 · ⛔ 남의 파일 커밋 금지.

## 세션 경계
- 플랫폼 세션(forge·forge-outputs)은 제품 코드를 고치지 않는다 — 제품 repo 일은 위임 브리프로.
- 세션은 연 프로젝트 **그리고** 이 PC(`pc:`) 몫만 작업한다(코드·장부·이슈·문서 모두). 범위 밖은 개수만 적는다. '다 해' 는 이 범위 안의 전부다.
- 작업 세션을 끝낼 때는 **요청이 없어도 `/forge-end`** 로 인수인계를 남긴다(팀장 방은 버스 교체 체크포인트가 대신한다).
- 끊겼다 이어갈 때 첫 행동은 실측 — `git log -3`·`gh pr view`·`tail <방>.send.jsonl` 로 마지막 비가역 행동이 실제로 됐는지 본 뒤 계속한다.
